# Бюро переселения привидений

Консоль оператора вымышленного агентства, которое расселяет привидений из старых зданий по
новым локациям. Приложение само предлагает лучшее место для каждой заявки, объясняет свой
выбор, показывает, почему кому-то место не нашлось, позволяет оператору переназначить любую
заявку вручную (с предупреждениями, но без блокировок) и строит итоговый отчёт.

Это учебный/демонстрационный проект: домен вымышленный, весь интерфейс — на русском, логика
и код — на английском.

## Стек

Vite + React + TypeScript, Vitest. Без бэкенда, без базы данных, без роутера, без UI-кита и
менеджера состояния. Данные — статичный типизированный массив в `src/data/`.

## Как запустить

```bash
npm install
npm run dev
```

Откроется по адресу, который выведет Vite (обычно `http://localhost:5173`).

## Как тестировать

```bash
npm run typecheck   # проверка типов
npm test            # Vitest с покрытием; 100% на src/domain/** обязательно
npm run build       # сборка (tsc -b && vite build)
npm run lint         # ESLint
```

Вся логика подбора живёт в `src/domain/` и является чистыми функциями без React, DOM и
`Date.now()` — время всегда передаётся параметром. `npm test` падает сам по себе, если
покрытие домена опустится ниже 100%.

## Пять сценариев

Подробно расписаны в [SCENARIOS.md](./SCENARIOS.md) в формате Дано/Когда/Тогда:

1. **Пустой список заявок** — понятное пустое состояние, отчёт показывает 0/0.
2. **Привидение, которому не подходит ни одно место** — Кассиан Чердаков заблокирован
   комбинацией условий (нужен чердак + боится зеркал), а не одним фатальным полем.
3. **Локация, которую хотят больше привидений, чем она вмещает** — Аграфена и Полина обе
   лучше всего подходят Подвалу типографии (вместимость 1); место достаётся той, у кого
   дедлайн раньше, вторую вытесняет на следующий вариант.
4. **Конфликт при ручном переназначении** — оператор может назначить кого угодно куда угодно;
   при конфликте приложение только предупреждает, никогда не блокирует.
5. **Итоговый отчёт** — размещено/не размещено, самые проблемные заявки, перегруженные
   локации.

Все пять всегда доступны из коробки на реальных стартовых данных — редактировать код для
этого не нужно.

## Алгоритм

Два независимых слоя, `evaluate(ghost, place, occupancy, now)`:

**Жёсткие ограничения** — любое нарушение делает место недоступным:

| проверка   | условие                         | причина (по-русски)              |
|------------|----------------------------------|-----------------------------------|
| вместимость | occupancy >= capacity           | «Нет свободных мест»              |
| дедлайн    | ghost.deadline < now             | «Дедлайн переселения просрочен»   |
| люди       | no_humans && hasHumans           | «В здании живут люди»             |
| чердак     | attic && !hasAttic               | «В здании нет чердака»            |
| зеркала    | no_mirrors && hasMirrors         | «В здании есть зеркала»           |
| свет       | needs_dark && light > 6          | «Слишком светло»                  |

**Мягкий балл** (0–100, только для подходящих мест):

```
distance      = temp < min ? min - temp : temp > max ? temp - max : 0
tempScore     = clamp(100 - distance * 8, 0, 100)
noiseScore    = clamp(100 - place.noise * ghost.anxiety, 0, 100)
humidityTarget = likes_damp ? 80 : 45
humidityScore = clamp(100 - |place.humidity - humidityTarget| * 1.5, 0, 100)
score = round(tempScore * 0.3 + noiseScore * 0.4 + humidityScore * 0.3)
```

`ghost.preferredTemp` — это диапазон `{ min, max }`, а не одна точка: температура внутри
диапазона всегда даёт `tempScore = 100`, а штраф считается от ближайшей границы.

`needs_quiet` не блокирует, а штрафует: если `place.noise > 5`, из балла вычитается 25 и
добавляется предупреждение «Шумно для этого привидения» (итоговый балл не уходит ниже 0).

**Распределение** (`assignAll`) — жадное: привидения сортируются по возрастанию дедлайна
(при равенстве — по убыванию тревожности), и каждое получает лучшее из ещё свободных мест на
момент своей очереди.

### Это не глобально оптимально — и вот честный пример

Жадный алгоритм смотрит только на текущую заявку и текущие свободные места, а не на всю
картину сразу. В стартовых данных Аграфена Мокрицына и Полина Сумеречная обе лучше всего
подходят Подвалу типографии (вместимость 1), причём у Полины балл там даже выше (85 против
84 у Аграфены). Но дедлайн у Аграфены раньше, поэтому место достаётся ей, а Полину вытесняет
в Заброшенный театр. Переставь их местами — суммарный балл был бы выше, но алгоритм этого не
видит: он решает по очереди, а не глобально. Та же ситуация показана в отчёте приложения и
записана в [WORKLOG.md](./WORKLOG.md) (этап 2).

## Структура

- `src/domain/` — вся логика подбора (чистые функции, 100% покрытие тестами).
- `src/data/` — стартовые данные: 9 мест и 17 привидений.
- `src/components/` — компоненты интерфейса; они только показывают результат работы домена и
  сами ничего не вычисляют.
- `SCENARIOS.md` — пять сценариев в формате Дано/Когда/Тогда.
- `WORKLOG.md` — журнал решений по этапам разработки (рендерится во вкладке «AI Worklog»).

## Деплой

`.github/workflows/deploy.yml` публикует собранное приложение на GitHub Pages при пуше в
`main` (нужно включить Pages → «GitHub Actions» в настройках репозитория). `vite.config.ts`
использует относительный `base`, поэтому сборка работает и с корня домена, и из подпапки
`/имя-репозитория/`.
